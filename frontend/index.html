P4 — AI Gallery Storage Pipeline: S3 + CloudFront + OAC

Secure, cost-conscious AWS storage pipeline for AI-generated images — built first by hand in the console to understand every moving part, then rebuilt as reproducible Infrastructure as Code with Terraform.

  • CloudFront Origin Access Control (OAC) as the only path to a fully private S3 bucket — Block Public Access on, ACLs disabled via BucketOwnerEnforced.
  • S3 bucket policy scoped with an AWS:SourceArn condition — trusts requests from this specific CloudFront distribution only, not "any CloudFront distribution."
  • Storage tiering by object prefix: S3 Intelligent-Tiering for full-resolution images, lifecycle transition to Glacier after 90 days for archived content, S3 Standard for thumbnails.
  • Every object encrypted server-side (SSE-S3); infrastructure fully codified in Terraform (AWS provider ~> 5.0).

Technical Challenge: Verified the security boundary end-to-end — a direct request to the S3 object URL returns AccessDenied, while the same object requested through the CloudFront domain resolves correctly, confirming the bucket policy's SourceArn condition trusts only this specific distribution rather than CloudFront broadly.

P5 — CloudWatch + SNS Monitoring

CloudWatch monitoring and alerting pipeline for an EC2 instance, built with Terraform following an ephemeral infrastructure methodology — built to validate the concept, then torn down.

  • CloudWatch Alarm on CPUUtilization (≥70%, 2 datapoints over 4 minutes) — requires sustained load before triggering, avoiding false positives from a single CPU spike.
  • SNS Topic decoupling the alarm (publisher) from the notification channel — a single topic emails on both ALARM and OK state changes, extensible to more subscribers or protocols without touching the alarm itself.
  • CloudWatch Dashboard with a live CPU widget for the monitored instance.
  • Zero SSH exposure — an IAM Role + Instance Profile with AmazonSSMManagedInstanceCore enables Session Manager access instead of an open port 22 or a key pair to manage.

Technical Challenge: terraform apply failed because the aws_subnets data source pulled every subnet in the default VPC and landed the instance in an Availability Zone where t2.micro isn't offered on this account. Fixed by adding an explicit availability-zone filter to the data source, restricting it to the AZs that actually support the instance type.

P6 — Multi-Region Disaster Recovery (Pilot Light)

Multi-region Disaster Recovery architecture using the Pilot Light pattern, 100% defined in Terraform, deployed across sa-east-1 (primary) and us-east-1 (DR), with a real, documented failover test.

  • 2 non-overlapping VPCs, 3-tier subnetting across 2 AZs x 2 regions; RDS MySQL Multi-AZ in primary with a cross-region Read Replica in DR.
  • ALB + Auto Scaling Group in both regions — primary active (desired=2), DR in Pilot Light (desired=0).
  • Route 53 Failover Routing with a Health Check on the primary ALB; automatic DNS failover on detection (~90s).
  • CloudWatch Alarms + SNS on Health Check status and RDS Replica Lag; no SSH — instance access exclusively via SSM.
  • 5 independent Terraform modules wired via aliased providers (aws.primary / aws.dr).

Technical Challenge: A cross-region encrypted RDS Read Replica doesn't inherit the primary region's KMS key — KMS keys are regional, so the DR replica needed its own explicit kms_key_id in us-east-1. Also surfaced that Route 53 health check metrics, despite being a global service, only publish to CloudWatch in us-east-1 regardless of the monitored region.

P2 — IAM in Depth: Zero Trust Identity Architecture

Zero Trust identity architecture on AWS — built ClickOps first, then fully codified in Terraform. Every permission flows through groups or roles; no user holds direct policies.

  • AWS Organizations with SCP enforcing region isolation at root level — blocks all actions outside sa-east-1, even for AdministratorAccess.
  • IAM Identity Center (SSO) with Permission Sets — centralized access replacing manual cross-account role assignments.
  • Permission Boundaries as a hard ceiling — developer persona cannot escalate beyond EC2 + CloudWatch regardless of identity policies.
  • STS AssumeRole for temporary credentials — no long-lived access keys on EC2 instances.
  • Custom policies: region-locked S3 access, explicit deny, MFA delete protection.

Technical Challenge: Self-inflicted access denial after removing direct permissions before group inheritance was fully applied. Resolved via root MFA authentication, state verification, and clean group-based access restoration — entirely through IaC, no manual policy changes.
